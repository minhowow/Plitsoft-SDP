# 라벨 기준서 (2026-11-03)

이 기준서는 공개 JS/TS 저장소의 (시작 파일, 정책) 단위에 정답 라벨을 붙이는 기준이다.
근거는 `legal/` 의 조문 원문 일곱 개뿐이다. 다른 자료는 보지 않고 썼다.
조문에서 바로 읽히지 않는 해석은 "잠정"으로, 주어진 발췌에 없는 내용은 "발췌 밖"으로 표시했다.

## 1. 무엇을 묻는가

한 단위는 시작 파일 하나와 정책 하나다. 묻는 것은 하나다.

> 이 시작 파일에서 일어나는 처리에 대해, 이 저장소의 코드를 보면 조문의 의무를 이행하는 처리가 보이는가.

- 법 위반인지 묻지 않는다. 코드에 무엇이 보이는지만 묻는다.
- 저장소 밖은 없는 것으로 본다. 운영 중인 웹사이트, 외부 문서, 외부 이메일 서비스에만 있는 템플릿, 사업자의 계약은 보지 않는다.
- 의무가 걸리는 처리는 **시작 파일에** 있어야 한다. 이행하는 처리는 **같은 저장소 어디에나** 있을 수 있다.

## 2. 기본 원칙

1. **처리만 근거가 된다.** 실행되는 코드, 그리고 이용자 화면에 보이는 문구(JSX 텍스트, 약관·처리방침 본문 문자열, 메시지 템플릿 문자열)가 처리다. 주석, README, 문서 파일(`*.md`, `docs/`)은 처리가 아니다.
2. **시험용 코드는 이행 근거가 아니다.** `*.test.*`, `*.spec.*`, `__tests__/`, 스토리북(`*.stories.*`), 목업·픽스처 데이터에 있는 처리는 제품의 이행으로 세지 않는다. 시작 파일 자체가 시험 파일이면 아래 범위 표시를 붙이고 평소대로 판정한다.
3. **같은 흐름이어야 한다.** 이행하는 처리는 시작 파일의 처리와 같은 앱(모노레포라면 같은 패키지나 그 패키지가 가져다 쓰는 공통 패키지)에 있어야 한다. 다른 앱의 동의 화면은 근거가 아니다.
4. **정의만 있고 쓰이지 않는 코드는 근거가 아니다.** 이행처럼 보이는 컴포넌트나 함수를 찾으면, 그 이름으로 한 번 검색해 쓰이는 곳이 있는지 본다. 쓰이는 곳이 하나도 없으면 근거로 쓰지 않는다. 화면 라우트(페이지 파일)와 서버 라우트는 파일이 있는 것만으로 쓰이는 것으로 본다.
5. **조문의 말로 판단한다.** 각 정책 절의 "의무가 걸리는 처리"와 "이행하는 처리"는 조문 문구를 인용해 정했다. 이름이 비슷하다는 것만으로 판정하지 않는다. 예: `marketingAgreed` 라는 필드가 있다고 야간 동의가 있는 것은 아니다.
6. **환경 변수와 설정.** 값이 코드나 저장소 안의 설정 파일(`.env.example`, 설정 상수)에 보이면 그 값을 쓴다. 저장소 안에서 기본값조차 보이지 않고, 그 값에 따라 의무가 걸리는지가 갈리면 "가를 수 없음"을 고려한다.

## 3. 값의 뜻

라벨러는 늘 아래 넷 가운데 하나를 고른다. JSON 에는 따옴표 안의 글자를 그대로 쓴다.

| 값 | 뜻 | 인용 |
|---|---|---|
| "검토 필요" | 의무가 걸리는 처리가 시작 파일에 있고, 찾기 기준(6절)을 다 따랐는데도 이행하는 처리가 저장소에 보이지 않는다. | 시작 파일에서 의무가 걸리는 처리의 줄을 하나 이상 |
| "충족 근거 있음" | 의무가 걸리는 처리가 시작 파일에 있고, 이행하는 처리가 저장소에 보인다. | 이행하는 처리의 줄을 하나 이상(다른 파일이면 그 파일) |
| "해당 없음" | 시작 파일이 그 정책의 의무가 걸리는 처리를 하지 않는다. | 없어도 된다. 판단에 쓴 줄을 적어도 된다. |
| "가를 수 없음" | 코드만으로 정말 가를 수 없다. 되도록 쓰지 않는다. | 없어도 된다. |

- "가를 수 없음"은 시작 파일이 무엇을 하는지 저장소 안의 코드로 알 수 없을 때만 쓴다. 예: 시작 파일이 압축·난독화되어 읽을 수 없다. 핵심 분기가 저장소 밖 설정에만 달려 있고 기본값도 없다.
- 도구 예산이 떨어졌다는 이유로 "가를 수 없음"을 쓰지 않는다. 6절의 예산 규칙을 따른다.
- 이행이 일부만 보이는 경우(조문이 요구하는 사항 가운데 일부만)는 정책 절이 따로 정하지 않는 한 "검토 필요"다.

## 4. 인용 규칙

- 인용 하나는 `{파일 경로, 줄 번호, 코드 원문}` 이다.
- 파일 경로는 저장소 루트 기준 상대 경로다.
- 줄 번호는 `read_file` 로 실제 읽은 줄 번호다. 짐작한 번호를 쓰지 않는다.
- 코드 원문은 그 줄의 글자를 그대로 옮긴다. 앞뒤 공백만 뺄 수 있다. 고쳐 쓰기, 요약, "..." 줄임을 하지 않는다.
- 여러 줄에 걸친 처리면 가장 핵심이 되는 줄 하나를 고르고, 필요하면 인용을 더 붙인다.
- "검토 필요"는 시작 파일의 줄을 인용한다. "충족 근거 있음"은 이행하는 줄을 인용한다. 이행 근거가 시작 파일에 있으면 시작 파일의 줄을 인용한다.

## 5. 값과 따로 붙이는 표시

### 5.1 범위 표시 (하나만)

| 표시 | 언제 |
|---|---|
| "시험·스토리 파일" | 시작 파일이 `*.test.*`, `*.spec.*`, `__tests__/` 안, `*.stories.*`, 목업·픽스처 데이터 파일이다. |
| "나이를 받지 않는 가입" | 정책 kr.pipa.22-2 에서만. 시작 파일이 생년월일·나이·연령대를 받지 않는 일반 가입(또는 회원 정보 등록) 처리다. |
| "없음" | 위 둘이 아니다. |

- 둘 다 맞으면 "시험·스토리 파일"을 붙인다.
- 표시가 붙어도 값은 "그 단위가 범위 안이라면 무엇인가"로 적는다. 범위에 넣을지는 채점 때 정한다. 표시를 이유로 "해당 없음"을 고르지 않는다.
- 예: 시험 파일 안에서 광고 문자를 보내는 함수를 부르고, 저장소 어디에도 야간 제한이 없다. 값은 "검토 필요", 범위는 "시험·스토리 파일"이다.

### 5.2 논쟁 있음

- 해석이 갈릴 수 있다고 보면 이유를 한 줄로 적는다. 없으면 `null` 이다.
- 각 정책 절에 "논쟁 있음을 붙이는 경우"를 적었다. 그 밖에도 라벨러가 판단해 붙일 수 있다.
- 논쟁 있음은 값을 바꾸지 않는다. 값은 기준서가 정한 쪽으로 고르고, 다른 해석이 있다는 것만 적는다.

## 6. 찾기와 멈추기 기준

이행하는 처리는 다른 파일에 있을 수 있다. 모든 파일을 읽을 수는 없으므로 아래 순서로 찾고, 정해진 곳에서 멈춘다.

**단계 0. 시작 파일 읽기.** 시작 파일을 끝까지 읽는다. 길면 나누어 읽는다.

**단계 1. 의무가 걸리는지 정하기.** 정책 절의 "의무가 걸리는 처리"에 맞는 처리가 시작 파일에 있는지 본다.
- 시작 파일이 부르는 함수가 무엇을 하는지 모르면, 그 함수가 있는 파일을 열어 볼 수 있다(최대 세 번).
- 의무가 걸리는 처리가 없으면 "해당 없음"으로 멈춘다. 이행을 찾지 않는다.

**단계 2. 시작 파일 안에서 이행 찾기.** 이행하는 처리가 시작 파일에 있으면 "충족 근거 있음"으로 멈춘다.

**단계 3. 가까운 파일.** 시작 파일이 직접 가져오는(import·require) 파일 가운데 이 처리와 관련된 것을 연다(최대 다섯). 프론트엔드 화면이면 그 화면을 감싸는 상위 페이지·레이아웃, 서버 라우트면 그 라우트에 걸린 미들웨어도 여기에 든다.

**단계 4. 저장소 검색.** 정책 절의 "찾을 낱말"을 한국어와 영어 모두 검색한다. 정책마다 최소 검색 횟수를 적었다. 검색에 걸린 파일 가운데 이행처럼 보이는 것을 연다(최대 다섯).

**단계 5. 약관·처리방침·동의 화면.** 파일 목록에서 이름이나 경로에 `terms`, `privacy`, `policy`, `consent`, `agree`, `legal`, `약관`, `개인정보`, `동의` 가 들어간 파일을 찾아, 이 정책과 관련 있어 보이는 것을 연다(최대 셋). 정책 절이 이 단계를 생략한다고 적은 경우는 건너뛴다.

**멈추기.**
- 이행하는 처리를 하나 찾으면 바로 멈춘다. 2절의 원칙 3, 4(같은 흐름, 쓰이는 코드)를 확인한 뒤 "충족 근거 있음"을 고른다.
- 단계 3~5를 다 했는데 이행이 없으면 멈추고 "검토 필요"를 고른다. 저장소의 나머지 파일을 더 뒤지지 않는다.
- 단계 3~5의 "최대" 수는 넘지 않아도 된다. 걸린 파일이 그보다 적으면 있는 만큼만 연다.

**예산.** 도구 호출은 단위당 30번까지다. 위 순서는 대개 20번 안에 끝난다. 예산이 떨어질 때까지 단계 5를 끝내지 못했으면, 그때까지 본 것으로 고른다. 의무가 걸리는 처리를 확인했고 이행을 못 찾았으면 "검토 필요"를 고르고, reason 에 "예산 안에서 찾기를 끝내지 못함"을 적는다.

## 7. 정책별 기준

각 정책 절은 라벨러 지시문의 `{{POLICY_SECTION}}` 자리에 그대로 들어간다. 절은 `## 정책` 으로 시작하는 줄부터 다음 `## 정책` 줄 앞까지다.

## 정책 kr.pipa.22-2 (개인정보 보호법 제22조의2, 아동의 개인정보와 법정대리인 동의)

### 조문

> ① 개인정보처리자는 만 14세 미만 아동의 개인정보를 처리하기 위하여 이 법에 따른 동의를 받아야 할 때에는 그 법정대리인의 동의를 받아야 하며, 법정대리인이 동의하였는지를 확인하여야 한다.

제2항(법정대리인 동의를 위한 최소 정보), 제3항(아동에게 쉬운 언어로 고지), 제4항(동의 확인 방법은 대통령령)이 있다. 이 라벨은 제1항만 본다.

### 의무가 걸리는 처리

조문의 말: "만 14세 미만 아동의 개인정보를 처리하기 위하여 이 법에 따른 동의를 받아야 할 때".

- 시작 파일이 **이용자에게서 개인정보를 받아 저장하거나 보내는 처리**를 한다. 가입, 회원 정보 등록, 프로필 작성, 동의 체크를 받는 폼과 그 서버 처리가 여기에 든다.
- 받는 항목은 이름, 이메일, 전화번호, 생년월일, 주소, 사진처럼 이용자에 관한 정보다.
- 생년월일·나이를 받으면 범위 표시 "없음", 받지 않으면 "나이를 받지 않는 가입"을 붙인다. 두 경우 모두 의무가 걸리는 처리로 본다.
- 잠정: 어떤 처리가 "이 법에 따른 동의를 받아야 할 때"인지는 다른 조문(동의 요건)에 달려 있고, 그 조문은 여기 없다(발췌 밖). 이 기준서는 이용자에게서 개인정보를 받는 가입·등록 처리를 동의가 필요한 처리로 본다.

해당 없음인 경우: 관리자만 쓰는 화면, 로그인(이미 가입한 계정의 인증만), 개인정보를 받지 않는 폼(검색어, 상품 필터), 서버 설정 파일.

### 이행하는 처리

조문의 말: "그 법정대리인의 동의를 받아야 하며, 법정대리인이 동의하였는지를 확인하여야 한다".

아래 가운데 하나가 시작 파일의 가입 흐름에 보이면 이행으로 본다.

1. **법정대리인 동의 흐름.** 나이(또는 생년월일)로 만 14세 미만을 가르고, 그 경우 법정대리인 동의를 받는 단계로 보낸다. 법정대리인의 동의 여부를 확인하는 처리(보호자 휴대폰 인증, 보호자 이메일 확인 링크, 동의 완료 플래그 확인 뒤 가입 완료)가 있어야 한다.
2. **만 14세 미만 가입 차단.** 나이로 만 14세 미만이면 가입을 막는다. 또는 "만 14세 이상입니다" 확인을 필수로 받고, 확인하지 않으면 가입을 진행하지 않는다. 이 경우 아동의 개인정보를 처리하지 않으므로 동의 의무가 생기지 않는 것으로 본다(잠정: 조문은 차단을 직접 말하지 않는다).

이행으로 보지 않는 것:
- 보호자 동의 체크박스만 있고 법정대리인이 동의했는지 확인하는 처리가 없다. 조문은 "확인하여야 한다"고 한다. 단, 이 경우는 논쟁 있음을 붙인다.
- 만 14세 확인 체크가 있지만 선택 항목이라 체크하지 않아도 가입이 된다.
- 나이 기준선이 만 14세보다 낮다(예: 만 13세 미만만 막거나 그때만 보호자 동의를 받음). 만 13세 아동은 그대로 통과하므로 이행이 아니다.
- 약관 본문에 "만 14세 미만은 법정대리인 동의가 필요합니다"라는 문구만 있고 가입 흐름에 나이 확인이 없다.

### 찾을 낱말 (단계 4, 최소 세 번 검색)

`법정대리인`, `보호자`, `14세`, `만 14`, `guardian`, `parent`, `under14`, `minor`, `child`, `age`, `birth`, `isMinor`, `ageGate`.

### 판정 예

1. 가입 폼이 이메일, 비밀번호, 닉네임만 받는다. 저장소에 나이 확인도 보호자 동의도 없다. 값 "검토 필요", 범위 "나이를 받지 않는 가입". 인용은 가입 요청을 보내는 줄.
2. 가입 폼이 생년월일을 받고, 같은 파일에서 `age < 14` 이면 `/signup/guardian` 으로 보낸다. 그 페이지가 보호자 휴대폰 인증 뒤 `guardianVerified: true` 를 저장하고 가입을 마친다. 값 "충족 근거 있음", 범위 "없음". 인용은 보호자 인증 결과를 확인하는 줄.
3. 가입 폼에 필수 체크 "만 14세 이상입니다"가 있고, 체크하지 않으면 가입 버튼이 비활성화된다. 값 "충족 근거 있음", 범위 "나이를 받지 않는 가입". 논쟁 있음: "자기 신고 체크만으로 아동 처리를 배제했다고 볼지 갈린다".
4. 생년월일을 받지만 나이로 분기하는 곳이 저장소 어디에도 없다. 값 "검토 필요", 범위 "없음".
5. 시작 파일이 로그인 처리다. 새 개인정보를 받지 않는다. 값 "해당 없음".
6. OAuth(구글·카카오) 가입만 있고, 받은 프로필(이름·이메일)을 저장한다. 나이 확인이 없다. 값 "검토 필요", 범위 "나이를 받지 않는 가입". 논쟁 있음: "외부 계정이 나이를 이미 확인했는지는 저장소 밖이다".

### 논쟁 있음을 붙이는 경우

- 보호자 동의 체크만 있고 확인 처리가 없을 때.
- 자기 신고 체크("만 14세 이상")만으로 차단할 때.
- 외부 계정 가입만 있을 때.

### 잠정·발췌 밖

- 동의가 필요한 경우의 범위: 발췌 밖(동의 요건 조문이 없다). 잠정 기준은 위와 같다.
- 동의 확인 방법(제4항의 대통령령): 발췌 밖. 어떤 확인 방법이 충분한지는 따지지 않는다. 확인하는 처리가 있으면 이행으로 본다.
- 제2항의 "대통령령으로 정하는 정보": 발췌 밖. 보호자 연락처를 아이에게서 받는 것 자체는 판정에 쓰지 않는다.

## 정책 kr.network-act.50-3 (정보통신망법 제50조 제3항, 야간 광고 전송의 별도 동의)

### 조문

> ③ 오후 9시부터 그 다음 날 오전 8시까지의 시간에 전자적 전송매체를 이용하여 영리목적의 광고성 정보를 전송하려는 자는 제1항에도 불구하고 그 수신자로부터 별도의 사전 동의를 받아야 한다. 다만, 대통령령으로 정하는 매체의 경우에는 그러하지 아니하다.

시행령 제61조 제2항: "법 제50조제3항 단서에서 "대통령령으로 정하는 매체"란 전자우편을 말한다."

### 의무가 걸리는 처리

조문의 말: "전자적 전송매체를 이용하여 영리목적의 광고성 정보를 전송하려는 자".

- 시작 파일이 **전자우편이 아닌 매체로 광고성 정보를 보내거나 보낼 일정을 잡는 처리**를 한다. 매체는 문자(SMS·LMS·MMS), 카카오 알림톡·친구톡, 앱 푸시(FCM, APNs, OneSignal, Expo), 웹 푸시 등이다.
- 광고성은 코드에서 보여야 한다. 메시지 문구, 함수·변수 이름, 수신 동의 필드 이름이 마케팅, 광고, 프로모션, 이벤트, 쿠폰, 할인, 캠페인, 뉴스레터를 가리키면 광고성으로 본다.
- 보내는 시각을 제한하지 않으면 야간에 보낼 수 있으므로 걸린다. 관리자가 발송 시각을 고르는 캠페인 도구도 걸린다.

해당 없음인 경우:
- 전자우편만 보낸다(단서와 시행령 제61조 제2항).
- 거래·서비스 메시지만 보낸다(주문 확인, 배송 알림, 인증번호, 비밀번호 재설정, 채팅 알림). 광고성이 코드에서 보이지 않는다.
- 시작 파일이 범용 발송 래퍼(`sendSms(to, text)`)이고 그 안에서 광고 여부를 정하지 않는다. 다른 파일이 이 래퍼로 광고를 보내는 것이 보이면 논쟁 있음을 붙인다.

### 이행하는 처리

조문의 말: "오후 9시부터 그 다음 날 오전 8시까지의 시간에 ... 별도의 사전 동의를 받아야 한다".

아래 가운데 하나가 시작 파일의 발송 경로에 보이면 이행으로 본다.

1. **야간 발송을 막거나 미룸.** 보내기 전에 현재 시각(또는 예약 시각)이 21시 이상이거나 8시 미만이면 보내지 않거나 8시 이후로 미룬다. 예약 입력에서 그 시간대를 고를 수 없게 막는 것도 든다.
2. **야간 별도 동의 확인.** 이용자에게서 야간 광고 수신에 대한 동의를 일반 광고 동의와 따로 받고, 야간 발송 때 그 동의를 확인해 동의한 사람에게만 보낸다.

이행으로 보지 않는 것:
- 일반 광고 수신 동의(`marketingAgreed`, `adConsent`)만 확인한다. 제3항은 "별도의" 동의를 요구한다. 이것은 제1항의 동의다.
- 야간 동의를 받는 화면은 있지만 발송 경로에서 그 값을 확인하지 않는다.
- 시간 창이 조문 시간을 덮지 못한다(예: 22시~7시만 막음).

### 찾을 낱말 (단계 4, 최소 세 번 검색)

`야간`, `21시`, `오후 9`, `night`, `nightConsent`, `quietHours`, `quiet`, `doNotDisturb`, `getHours`, `hour`, `21`, `Asia/Seoul`, `KST`, `광고성`, `수신 동의`.

### 판정 예

1. 쿠폰 푸시를 FCM 으로 보내는 함수가 시각을 확인하지 않는다. 저장소에 야간 제한도, 야간 동의도 없다. 값 "검토 필요". 인용은 발송 호출 줄.
2. 같은 함수가 `const h = dayjs().tz('Asia/Seoul').hour(); if (h >= 21 || h < 8) return schedule(nextMorning8)` 을 거친다. 값 "충족 근거 있음". 인용은 시간 확인 줄.
3. 마케팅 이메일 뉴스레터 발송만 한다. 값 "해당 없음"(전자우편은 단서에 해당).
4. 야간 제한이 `new Date().getHours() >= 21` 인데 서버 시간대가 코드에서 보이지 않는다. 값 "충족 근거 있음". 논쟁 있음: "서버 시간대가 한국 시간이 아니면 창이 어긋난다".
5. 주문 완료 알림톡만 보낸다. 값 "해당 없음".
6. 관리자 캠페인 화면에서 문자 발송 예약 시각을 자유롭게 고르고, 서버도 시각을 확인하지 않는다. 값 "검토 필요".

### 논쟁 있음을 붙이는 경우

- 시간 확인이 있지만 기준 시간대가 코드에서 보이지 않을 때.
- 광고성인지 거래 메시지인지 문구로 갈리기 어려울 때(예: "새 상품이 입고되었어요").
- 시작 파일이 범용 발송 래퍼이고 다른 곳에서 광고에 쓰일 때.

### 잠정·발췌 밖

- 앱 푸시가 "전자적 전송매체"에 드는지: 조문은 매체를 나열하지 않는다. 잠정으로 문자·메신저·앱 푸시·웹 푸시를 모두 든다고 본다.
- 별도 동의를 받는 방법의 세부: 조문과 주어진 시행령에 없다. 따로 받고 따로 확인하면 이행으로 본다.

## 정책 kr.network-act.50-4 (정보통신망법 제50조 제4항, 광고성 정보에 밝힐 사항)

### 조문

> ④ 전자적 전송매체를 이용하여 영리목적의 광고성 정보를 전송하는 자는 대통령령으로 정하는 바에 따라 다음 각 호의 사항 등을 광고성 정보에 구체적으로 밝혀야 한다.
> 1. 전송자의 명칭 및 연락처
> 2. 수신의 거부 또는 수신동의의 철회 의사표시를 쉽게 할 수 있는 조치 및 방법에 관한 사항

시행령 제61조 제3항: 명시할 사항과 그 방법은 "별표 6과 같다". 시행령 제62조: 수신거부·철회용 무료전화서비스 등을 "해당 정보에 명시하여" 제공한다. 별표 6 원문은 여기 없다.

### 의무가 걸리는 처리

조문의 말: "전자적 전송매체를 이용하여 영리목적의 광고성 정보를 전송하는 자".

- 시작 파일이 **광고성 정보를 보내는 처리**를 한다. 매체는 전자우편을 **포함해** 문자, 알림톡·친구톡, 앱 푸시, 웹 푸시 모두다. 제4항에는 전자우편 단서가 없다.
- 광고성은 코드에서 보여야 한다. 문구, 함수·변수 이름, 수신 동의 필드 이름이 마케팅·광고·프로모션·이벤트·쿠폰·할인·캠페인·뉴스레터를 가리켜야 한다.

해당 없음인 경우: 거래·서비스 메시지만 보낸다(주문 확인, 인증번호, 비밀번호 재설정). 광고성이 코드에서 보이지 않는다. 시작 파일이 범용 발송 래퍼이고 그 안에서 광고 여부를 정하지 않는다(다른 파일이 이 래퍼로 광고를 보내면 논쟁 있음).

### 이행하는 처리

조문의 말: "전송자의 명칭 및 연락처", "수신의 거부 또는 수신동의의 철회 의사표시를 쉽게 할 수 있는 조치 및 방법".

시작 파일이 보내는 광고 메시지의 본문 또는 그 본문에 붙는 공통 머리말·꼬리말(템플릿, 레이아웃, 발송 함수가 덧붙이는 문자열)에 아래 셋이 **모두** 보이면 이행으로 본다.

1. 전송자의 명칭(회사명, 서비스명).
2. 전송자의 연락처(전화번호, 이메일 주소, 주소 가운데 하나 이상).
3. 수신거부 또는 수신동의 철회 방법(수신거부 링크, 수신거부 번호, "설정 > 알림에서 끌 수 있습니다" 같은 경로 안내).

- 이메일 발송 서비스의 자동 수신거부 기능을 코드에서 켜면(예: 발송 옵션에 수신거부 링크 삽입 설정) 3번으로 본다.
- 셋 가운데 하나라도 빠지면 "검토 필요"다. 인용은 시작 파일의 발송 줄 또는 템플릿 줄.

이행으로 보지 않는 것:
- 본문 앞의 "(광고)" 표기만 있다. 표기 방식은 별표 6에 맡겨져 있어 이 기준서는 요구하지도, 충분한 근거로 보지도 않는다(잠정).
- 메시지 본문이 저장소 밖(외부 이메일 서비스의 템플릿 ID만 있음)에 있다. 저장소 밖은 없는 것으로 본다.
- 앱 설정 화면에 알림 끄기 토글이 있지만 광고 메시지 자체에 그 방법이 적혀 있지 않다. 조문은 "광고성 정보에" 밝히라고 한다.

### 찾을 낱말 (단계 4, 최소 세 번 검색)

`수신거부`, `수신 거부`, `080`, `unsubscribe`, `opt-out`, `optout`, `footer`, `고객센터`, `문의`, `사업자`, `(광고)`, `광고`, `template`, `layout`.

단계 5(약관·처리방침)는 이 정책에서 생략한다. 약관은 광고 메시지가 아니다.

### 판정 예

1. 뉴스레터 HTML 템플릿 꼬리말에 회사명, 고객센터 이메일, `{{unsubscribe_url}}` 링크가 있다. 시작 파일이 이 템플릿으로 보낸다. 값 "충족 근거 있음". 인용은 수신거부 링크 줄(필요하면 명칭·연락처 줄도).
2. 프로모션 문자 문구가 `"[OO마켓] 주말 30% 할인! 바로가기 https://..."` 뿐이다. 값 "검토 필요". 인용은 문구 줄.
3. 이벤트 푸시 문구에 앱 이름과 "수신거부: 설정 > 알림"이 있지만 연락처가 없다. 값 "검토 필요". 논쟁 있음: "앱 푸시의 명시 사항은 별표 6에 맡겨져 있다".
4. 광고 메일을 외부 서비스 템플릿 ID 로만 보내고 본문은 저장소에 없다. 값 "검토 필요". 논쟁 있음: "본문이 저장소 밖에 있다".
5. 비밀번호 재설정 메일만 보낸다. 값 "해당 없음".
6. 문자 본문 앞에 "(광고)"와 회사명, 끝에 "무료수신거부 080-xxx-xxxx"가 있고, 연락처가 따로 없다. 값 "검토 필요"(연락처가 빠짐). 논쟁 있음: "수신거부 번호를 연락처로 볼지 갈린다".

### 논쟁 있음을 붙이는 경우

- 앱 푸시·웹 푸시에서 셋 가운데 일부만 있을 때.
- 본문이 저장소 밖에 있을 때.
- 수신거부 번호나 링크를 연락처로 겸할 수 있는지 갈릴 때.

### 잠정·발췌 밖

- 잠정: 명시 사항의 표기 위치, 글자 방식, "(광고)" 표기, 앱 푸시의 명칭과 수신거부 방법은 시행령 별표 6에 맡겨져 있고 원문이 없다. 이 기준서는 조문 제1호·제2호에서 읽히는 세 가지(명칭, 연락처, 수신거부 방법)만 요구한다.
- 잠정: 조문의 "사항 등"의 "등"이 무엇을 더 포함하는지 알 수 없다. 더 요구하지 않는다.
- 잠정: 시행령 제62조의 "무료전화서비스 등"의 구체적 범위는 별표 6에 있다. 수신거부 방법이 무료인지는 따지지 않는다.

## 정책 kr.ai-basic-act.31 (인공지능기본법 제31조 제2항·제3항, 생성형 AI 결과물 표시)

### 조문

> ② 인공지능사업자는 생성형 인공지능 또는 이를 이용한 제품 또는 서비스를 제공하는 경우 그 결과물이 생성형 인공지능에 의하여 생성되었다는 사실을 표시하여야 한다.
> ③ 인공지능사업자는 인공지능시스템을 이용하여 실제와 구분하기 어려운 가상의 음향, 이미지 또는 영상 등의 결과물을 제공하는 경우 해당 결과물이 인공지능시스템에 의하여 생성되었다는 사실을 이용자가 명확하게 인식할 수 있는 방식으로 고지 또는 표시하여야 한다.

시행령 제23조 제2항: 표시는 "1. 사람이 인식할 수 있는 방법" 또는 "2. 기계가 판독할 수 있는 방법. 이 경우 그 결과물이 생성형 인공지능에 의하여 생성되었다는 사실을 1회 이상 안내 문구ㆍ음성 등으로 제공해야 한다."
시행령 제23조 제4항 예외: "1. ... 생성형 인공지능을 활용한 사실이 명백한 경우", "2. 인공지능사업자의 내부 업무 용도로만 사용되는 경우".

### 의무가 걸리는 처리

조문의 말: "생성형 인공지능 또는 이를 이용한 제품 또는 서비스를 제공하는 경우 그 결과물".

- 시작 파일이 **생성형 AI 의 결과물을 이용자에게 내보내는 처리**를 한다. LLM 응답 텍스트를 화면에 보여주거나 API 응답으로 돌려준다. 생성 이미지·음성·영상을 돌려준다. 생성한 글을 이용자에게 메일·메시지로 보낸다.
- 생성형 AI 는 코드의 SDK·API 이름으로 판단한다(예: `openai`, `@anthropic-ai/sdk`, `@google/generative-ai`, `ai`(Vercel AI SDK), `langchain`, 이미지 생성 API, TTS API).
- 서버 라우트가 결과물을 돌려주기만 해도 걸린다. 표시는 그 응답을 그리는 화면에 있을 수 있다.
- 실제와 구분하기 어려운 음향·이미지·영상(사람 목소리 합성, 사진 같은 이미지, 영상)이면 제3항도 걸린다. 이때는 "이용자가 명확하게 인식할 수 있는 방식"이어야 한다.

해당 없음인 경우:
- 결과물이 이용자에게 가지 않는다. 분류, 임베딩, 검색 색인, 스팸 판정, 로그 요약을 내부에만 쓴다.
- 생성형이 아닌 AI(규칙 엔진, 추천 점수)만 쓴다.
- 인공지능사업자의 내부 업무 용도로만 쓴다(시행령 제23조 제4항 제2호). 코드에서 관리자 전용 화면·내부 도구로 보여야 한다.

### 이행하는 처리

조문의 말: "그 결과물이 생성형 인공지능에 의하여 생성되었다는 사실을 표시".

아래 가운데 하나가 시작 파일의 결과물이 이용자에게 보이는 경로에 있으면 이행으로 본다.

1. **사람이 인식하는 표시.** 결과물 옆이나 안에 "AI가 생성한", "AI 답변", "Generated by AI" 같은 문구·배지가 보인다. 음성이면 안내 음성.
2. **기계 판독 표시와 안내 문구.** 결과물에 메타데이터·워터마크(예: 이미지 메타데이터에 생성 사실 기록, 콘텐츠 출처 표시 표준)를 넣고, 그와 함께 생성 사실을 이용자에게 한 번 이상 문구로 안내한다. 메타데이터만 있고 안내 문구가 없으면 이행이 아니다(시행령 제23조 제2항 제2호).
3. **사실이 명백함.** 결과물이 보이는 화면의 제품·서비스명이나 문구가 생성형 AI 를 활용한 사실을 밝힌다(예: 화면 제목 "AI 어시스턴트", 입력창 "AI에게 물어보세요"). 시행령 제23조 제4항 제1호에 따라 표시 의무를 적용하지 않을 수 있는 경우다. 그 문구를 인용하고 "충족 근거 있음"을 고른다.

이행으로 보지 않는 것:
- 이용약관에만 "일부 기능은 AI를 사용합니다"가 있다. 그것은 제1항의 사전 고지이고 결과물 표시가 아니다.
- 모델 이름만 코드 상수에 있고 화면에 보이지 않는다.
- 제3항 대상(사실 같은 이미지·음성)인데 작은 툴팁 안에만 표시가 있다. "명확하게 인식할 수 있는 방식"인지 갈리므로 논쟁 있음을 붙이고 값은 "충족 근거 있음"으로 둔다.

### 찾을 낱말 (단계 4, 최소 세 번 검색)

`AI`, `인공지능`, `생성`, `generated`, `AI-generated`, `badge`, `label`, `disclaimer`, `watermark`, `c2pa`, `metadata`, `assistant`.

단계 5에서는 약관보다 결과물을 그리는 컴포넌트(메시지 말풍선, 결과 카드, 이미지 뷰어)를 먼저 찾는다.

### 판정 예

1. 서버 라우트가 OpenAI 응답을 스트리밍한다. 채팅 화면 제목이 "AI 상담봇"이고 각 답변 말풍선에 "AI" 배지가 있다. 값 "충족 근거 있음". 인용은 배지 JSX 줄.
2. 상품 설명을 LLM 으로 만들어 상품 상세 페이지에 그대로 보여준다. 화면 어디에도 AI 생성 표시가 없다. 값 "검토 필요". 인용은 생성 결과를 저장하거나 돌려주는 시작 파일의 줄.
3. 리뷰를 LLM 으로 긍정·부정 분류해 관리자 통계에만 쓴다. 값 "해당 없음".
4. 이미지 생성 API 결과를 내려받게 하는데, 메타데이터에 생성 사실을 쓰기만 하고 화면 안내가 없다. 값 "검토 필요". 논쟁 있음: "기계 판독 표시만 있고 1회 안내 문구가 보이지 않는다".
5. 고객 문의에 대한 답 메일 초안을 LLM 이 쓰고 상담원이 고친 뒤 보낸다. 값은 시작 파일이 초안을 그대로 보내면 "검토 필요", 상담원 화면에만 보이면 "해당 없음". 논쟁 있음: "사람이 고친 결과물을 생성형 결과물로 볼지 갈린다".
6. 서비스 이름이 "OO GPT"이고 화면에 다른 표시가 없다. 값 "충족 근거 있음". 논쟁 있음: "제품명만으로 사실이 명백한지 갈린다".

### 논쟁 있음을 붙이는 경우

- 명백함 예외에 기대는데 근거가 제품명 하나뿐일 때.
- 사람이 고친 결과물, 일부만 생성된 결과물.
- 제3항 대상의 표시가 눈에 잘 띄지 않을 때.

### 잠정·발췌 밖

- "인공지능사업자", "생성형 인공지능", "인공지능시스템"의 정의 조문은 여기 없다(발췌 밖). 잠정으로, 생성형 AI 를 써서 이용자에게 결과물을 내보내는 제품을 만든 쪽을 인공지능사업자로 본다.
- 시행령 제23조 제4항 제3호의 장관 고시: 발췌 밖. 판정에 쓰지 않는다.
- 제3항 단서(예술적·창의적 표현물의 표시 방식): 코드로 가르기 어렵다. 해당하면 논쟁 있음으로 적는다.

## 정책 kr.ai-basic-act.31-1 (인공지능기본법 제31조 제1항, 생성형 AI 기반 서비스의 사전 고지)

### 조문

> ① 인공지능사업자는 고영향 인공지능이나 생성형 인공지능을 이용한 제품 또는 서비스를 제공하려는 경우 제품 또는 서비스가 해당 인공지능에 기반하여 운용된다는 사실을 이용자에게 사전에 고지하여야 한다.

시행령 제23조 제1항 고지 방법: "1. 제품등에 직접 기재하거나 계약서, 사용 설명서, 이용약관 등에 기재", "2. 이용자의 화면 또는 단말기 등에 표시", "3. 제품등을 제공하는 장소 ... 에 인식하기 쉬운 방법으로 게시", "4. 그 밖에 ... 과학기술정보통신부장관이 인정하는 방법".
시행령 제23조 제4항 예외: "1. ... 생성형 인공지능을 활용한 사실이 명백한 경우", "2. 인공지능사업자의 내부 업무 용도로만 사용되는 경우".

### 의무가 걸리는 처리

조문의 말: "생성형 인공지능을 이용한 제품 또는 서비스를 제공하려는 경우".

- 시작 파일이 **생성형 AI 를 써서 이용자에게 기능을 제공하는 처리**를 한다. 이용자 요청을 받아 LLM·이미지 생성·음성 합성을 부르고 그 결과로 기능이 돌아간다.
- 결과물이 그대로 보이지 않아도, 이용자가 쓰는 기능이 생성형 AI 에 기반해 돌아가면 걸린다(예: AI 가 쓴 요약으로 검색 결과를 고름). 이 점이 제2항과 다르다.
- 고영향 인공지능도 조문에 있지만 정의가 여기 없다(발췌 밖). 이 정책은 생성형 AI 만 본다.

해당 없음인 경우: 생성형 AI 를 부르지 않는다. 내부 업무 용도로만 쓴다(관리자 전용, 개발용 스크립트). 이용자가 없는 배치 작업으로 내부 자료만 만든다.

### 이행하는 처리

조문의 말: "해당 인공지능에 기반하여 운용된다는 사실을 이용자에게 사전에 고지".

아래 가운데 하나가 저장소에 보이고, 이용자가 그 기능을 쓰기 **전에** 볼 수 있으면 이행으로 본다.

1. **이용약관·사용 설명 문구.** 저장소 안 약관·서비스 소개·도움말 본문 문자열에 이 서비스(또는 이 기능)가 생성형 AI 를 쓴다는 문장이 있다(시행령 제23조 제1항 제1호).
2. **화면 표시.** 기능을 쓰기 전 화면(입력창, 시작 화면, 온보딩, 기능 진입 버튼)에 AI 기반임을 알리는 문구가 있다(제2호).
3. **사실이 명백함.** 기능 이름이나 화면 문구가 생성형 AI 를 쓴다는 것을 밝힌다(예: "AI로 요약하기" 버튼). 시행령 제23조 제4항 제1호.

- "사전에"를 확인한다. 결과가 나온 뒤에만 보이는 표시(답변 아래 "AI 생성" 배지)는 제2항의 표시다. 단, 그 배지가 같은 화면에서 다음 요청 전에 늘 보이는 구조(채팅 화면)라면 화면 문구로 보고 이행으로 세되 논쟁 있음을 붙인다.

이행으로 보지 않는 것:
- README 나 개발 문서에만 AI 사용이 적혀 있다.
- 약관 파일이 있지만 AI 언급이 없다.
- 모델·제공자 이름이 코드 상수에만 있다.

### 찾을 낱말 (단계 4, 최소 세 번 검색)

`AI`, `인공지능`, `생성형`, `GPT`, `이용약관`, `terms`, `about`, `onboarding`, `placeholder`, `powered by`, `기반`.

### 판정 예

1. 글쓰기 도우미 화면 입력창 위에 "이 기능은 생성형 AI로 동작합니다"가 있다. 값 "충족 근거 있음". 인용은 그 JSX 텍스트 줄.
2. 상품 추천 문구를 LLM 이 만들어 홈 화면에 보여준다. 약관과 화면에 AI 언급이 없다. 값 "검토 필요".
3. 이용약관 본문 문자열에 "회사는 서비스 일부에 생성형 인공지능을 사용합니다"가 있고, 가입 때 약관 동의를 받는다. 값 "충족 근거 있음". 인용은 약관 문자열 줄.
4. 사내 운영팀만 쓰는 관리자 페이지에서 LLM 으로 공지 초안을 만든다. 값 "해당 없음".
5. 채팅 화면에 "AI 답변" 배지만 답변 아래에 있다. 값 "충족 근거 있음". 논쟁 있음: "배지가 첫 사용 전에 보이는지 갈린다".
6. 고객센터 챗봇이 LLM 으로 답하는데 화면은 "상담원"이라는 이름만 쓴다. 값 "검토 필요".

### 논쟁 있음을 붙이는 경우

- 표시가 첫 사용 뒤에만 보일 때.
- 명백함 예외에 기대는데 근거가 이름 하나뿐일 때.
- 약관이 AI 를 막연하게만 언급할 때(예: "자동화된 기술").

### 잠정·발췌 밖

- 고영향 인공지능의 정의: 발췌 밖. 판정하지 않는다.
- 시행령 제23조 제1항 제3호(장소 게시)와 제4호(장관이 인정하는 방법): 코드로 볼 수 없거나 발췌 밖이다. 쓰지 않는다.
- 잠정: 약관 문구가 가입 흐름에서 동의를 받지 않더라도, 저장소 안 화면에서 이용자가 열어 볼 수 있으면 "이용약관 등에 기재"로 본다.

## 정책 kr.pipa.ai-transfer (개인정보 보호법 제26조·제28조의8, 외부 AI 서비스로 보내는 개인정보)

### 조문 (발췌)

> 제26조 ② ... 위탁자는 위탁하는 업무의 내용과 ... 수탁자 ... 를 정보주체가 언제든지 쉽게 확인할 수 있도록 대통령령으로 정하는 방법에 따라 공개하여야 한다.
> 제28조의8 ① 개인정보처리자는 개인정보를 국외로 제공(조회되는 경우를 포함한다)ㆍ처리위탁ㆍ보관 ... 하여서는 아니 된다. 다만 ... 1. 정보주체로부터 국외 이전에 관한 별도의 동의를 받은 경우 … 3. 정보주체와의 계약의 체결 및 이행을 위하여 개인정보의 처리위탁ㆍ보관이 필요한 경우로서 ... 가. 제2항 각 호의 사항을 제30조에 따른 개인정보 처리방침에 공개한 경우 …
> 제28조의8 ② ... 동의를 받을 때에는 미리 다음 각 호의 사항을 정보주체에게 알려야 한다. 1. 이전되는 개인정보 항목 2. 개인정보가 이전되는 국가, 시기 및 방법 3. 개인정보를 이전받는 자의 성명(법인인 경우에는 그 명칭과 연락처를 말한다) 4. ... 이용목적 및 보유ㆍ이용 기간 5. 개인정보의 이전을 거부하는 방법, 절차 및 거부의 효과

### 의무가 걸리는 처리

조문의 말: "개인정보의 처리 업무를 위탁"(제26조), "개인정보를 국외로 제공 ... ㆍ처리위탁ㆍ보관"(제28조의8).

- 시작 파일이 **이용자의 개인정보를 외부 AI 서비스 API 로 보내는 처리**를 한다.
- 외부 AI 서비스: 저장소 운영자 밖의 사업자가 운영하는 AI API. SDK 이름이나 API 주소로 판단한다(예: `openai`, `api.openai.com`, `@anthropic-ai/sdk`, `generativelanguage.googleapis.com`, Azure OpenAI 엔드포인트, Replicate, Hugging Face 추론 API, 국내 AI API).
- 이용자의 개인정보: 이름, 이메일, 전화번호, 주소, 생년월일, 이용자 ID 와 묶인 기록, 이용자가 올린 사진·음성·문서, 이용자 프로필을 넣은 프롬프트.
- 이용자가 직접 쓴 자유 텍스트(채팅 메시지)만 보내면 걸리는 것으로 보고 논쟁 있음을 붙인다. 내용에 따라 개인정보인지 갈린다.
- **국외 이전 여부**는 API 주소·SDK 이름으로만 정한다. 국외 사업자의 API(위 예의 대부분)면 제28조의8 도 걸린다. 국내 사업자 API 나 국내 리전이 코드에 명시된 경우면 제26조만 걸린다.

해당 없음인 경우:
- 보내는 데이터에 이용자 정보가 없다(고정 프롬프트, 공개 상품 정보, 코드, 운영자가 쓴 글).
- 같은 저장소가 운영하는 자기 서버의 모델(localhost, 자체 호스팅 추론 서버)로만 보낸다. 외부 사업자가 없다.
- 개인정보를 지우거나 가린 뒤 보내는 것이 코드에 보인다(이름·전화번호 마스킹). 가린 범위가 부족해 보이면 논쟁 있음.

### 이행하는 처리

제26조 제2항의 말: "위탁하는 업무의 내용과 ... 수탁자를 정보주체가 언제든지 쉽게 확인할 수 있도록 ... 공개".
제28조의8 의 말: "국외 이전에 관한 별도의 동의를 받은 경우", "제2항 각 호의 사항을 ... 개인정보 처리방침에 공개한 경우".

아래가 저장소 안 이용자에게 보이는 문구(처리방침 화면·문자열, 동의 화면)에 있으면 이행으로 본다.

1. **국내 사업자(제26조만):** 그 AI 서비스(또는 사업자)를 수탁자로 밝히고, 맡기는 업무 내용을 적는다.
2. **국외 사업자(제26조와 제28조의8):** 1에 더해, 국외로 이전된다는 사실과 이전받는 자를 밝힌다. 방식은 둘 가운데 하나다.
   - 처리방침에 제28조의8 제2항 각 호의 사항(항목, 국가·시기·방법, 받는 자, 목적·기간, 거부 방법)을 공개한다.
   - 보내기 전에 국외 이전에 대한 별도 동의를 받고, 동의 화면에서 같은 사항을 미리 알린다. 동의가 없으면 보내지 않는 처리가 보여야 한다.
- 받는 자를 밝히고 국외 이전 사실(국가 또는 "국외")을 밝혔지만 다섯 사항 가운데 일부가 빠졌으면 값은 "충족 근거 있음"으로 두고, 논쟁 있음에 빠진 사항을 적는다.

이행으로 보지 않는 것:
- 처리방침에 "제3자 서비스를 이용할 수 있습니다"처럼 받는 자를 밝히지 않는 문장만 있다.
- 처리방침이 다른 수탁자(결제, 클라우드)만 나열하고 AI 서비스가 없다.
- 일반 서비스 이용약관 동의만 받는다. 제28조의8 제1항 제1호는 "별도의" 동의다.
- 처리방침이 저장소 밖 링크(외부 노션 페이지 등)로만 있다. 저장소 밖은 없는 것으로 본다.

### 찾을 낱말 (단계 4, 최소 네 번 검색)

`처리방침`, `개인정보처리방침`, `위탁`, `수탁`, `국외`, `이전`, `privacy`, `subprocessor`, `processor`, `third party`, `OpenAI`, `Anthropic`, `Google`, 그리고 시작 파일이 부르는 AI 사업자의 이름.

### 판정 예

1. 상담 챗봇이 이용자의 이름과 주문 내역을 프롬프트에 넣어 OpenAI API 로 보낸다. 처리방침 페이지에 결제·호스팅 수탁자만 있다. 값 "검토 필요". 인용은 프롬프트에 이름을 넣는 줄 또는 API 호출 줄.
2. 같은 처리인데 처리방침 문자열에 "수탁자: OpenAI, L.L.C. / 위탁 업무: 상담 답변 생성 / 이전 국가: 미국 / 이전 항목: 이름, 문의 내용 / 거부 방법: ..."이 있다. 값 "충족 근거 있음". 인용은 수탁자 줄.
3. 이력서 PDF 를 받아 Anthropic API 로 요약한다. 업로드 전 "국외 이전 동의" 체크가 필수이고 동의 화면에 국가·받는 자·항목이 있다. 값 "충족 근거 있음". 인용은 동의 문구 줄.
4. 이용자가 자기 API 키를 넣고, 브라우저가 OpenAI 를 직접 부른다. 값 "검토 필요"(처리방침 문구가 없을 때). 논쟁 있음: "이용자 키로 직접 부르면 운영자가 위탁자인지 갈린다".
5. 자체 서버의 오픈소스 모델(`http://localhost:11434`)로만 보낸다. 값 "해당 없음".
6. 공개 상품 설명만 보내 마케팅 문구를 만든다. 값 "해당 없음".
7. 채팅 메시지 원문만 보낸다(이용자 ID 등은 안 보냄). 처리방침에 AI 서비스가 없다. 값 "검토 필요". 논쟁 있음: "자유 입력 텍스트가 개인정보인지 내용에 따라 갈린다".

### 논쟁 있음을 붙이는 경우

- 자유 입력 텍스트만 보낼 때.
- 이용자 키(BYOK)로 직접 부를 때.
- 처리방침이 받는 자를 밝혔지만 다섯 사항 일부가 빠졌을 때(빠진 사항을 적는다).
- 마스킹이 있지만 충분한지 갈릴 때.

### 잠정·발췌 밖

- 발췌 밖: 제26조 제1항(위탁 문서), 시행령 제28조 제2항·제4항의 공개·통지 방법, 시행령 제29조의7, 제28조의8 제1항의 다른 호, 제30조(처리방침)의 내용. 이 기준서는 공개 방법의 세부를 따지지 않는다. 저장소 안에서 이용자가 볼 수 있는 문구에 있으면 공개로 본다.
- 발췌 밖: 외부 AI 서비스로 보내는 것이 "위탁"인지 "제3자 제공"인지를 가르는 기준. 잠정으로 위탁으로 본다(외부 사업자가 운영자의 업무를 대신 처리).
- 잠정: 국외 여부는 API 주소·SDK 이름으로만 판단한다. 리전 설정이 코드에 없으면 사업자 소재지로 판단한다.
- 제26조 제3항(홍보·판매 권유 위탁의 통지)은 AI 로 광고 문구를 만들고 이용자 정보를 넣을 때 걸릴 수 있으나, 이 정책의 판정에는 쓰지 않는다.
